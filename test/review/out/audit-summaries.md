# Static audit — per-subsystem verdicts

## select-transform — Grade C (fixable)

The selection model itself (src/model/selection.ts) is clean and sound: a small observable store of Element refs plus a transform-aware overlay renderer. The transform tools, however, are riddled with coordinate-space confusion between an element's LOCAL attribute space and DOC space, and they special-case "single un-transformed element" everywhere, so anything with a pre-existing transform (PDF-imported matrix(), translated/scaled groups, rotated shapes) gets corrupted or jumps. The worst offenders are: free-transform rotate silently dropping translate/scale from a matrix transform (data corruption), reflect using a doc-space AABB center against local-space coordinates for transformed elements (mirror placed wrong), and multi-select scale ignoring per-element transforms. The undo/redo plumbing (reset-then-execute via ModifyAttributeCommand) is correct and consistent across both tools, selection is properly cleared after Delete, and INPUT/TEXTAREA focus is guarded in every keyboard path — so the historical focus-stealing and stale-ref fault-lines do NOT recur here. This is fixable, not a rewrite: the bugs are concentrated in a handful of transform-composition spots that all share the same root cause (mixing local and doc coordinate frames). A single helper that consistently maps anchor/center/mouse into the element's local space before mutating local attributes would kill most of them.

_Architecture:_ The design is fundamentally sound and under-engineered in the good sense: selection is a tiny observable store of live DOM Element references with a RAF-coalesced overlay renderer, and all mutations route through ModifyAttributeCommand/CompoundCommand using a disciplined reset-then-execute pattern that makes undo/redo correct and uniform across both tools. The historical fault-lines the owner worries about are NOT present here — INPUT/TEXTAREA focus is guarded in every keyboard handler (Canvas, EditorContext, useToolShortcuts), Delete clears selection so no stale refs survive, and _-prefixed params (_getDoc) are genuinely unused pass-throughs. The real architectural weakness is the absence of a single coordinate-frame abstraction: every transform operation hand-rolls local-vs-doc-space mapping and special-cases "single untransformed element," which is why the same class of bug (doc-space anchor/center applied to local-space attributes) recurs in selectTool scale, reflect, and free-transform. selectTool and freeTransformTool also duplicate ~70% of their scale/rotate/commit logic with subtle divergences (findings 1, 8, 9). Testability is decent for the pure model layer (selection.ts, matrix.ts, reflect.ts have unit tests) but the tools are DOM/event-heavy and only validated via the dogfood/golden suites; the transform-composition bugs above are exactly the kind unit tests should pin down. Recommendation: extract one toLocalFrame(el, point) helper and one composeTransform(el, matrix) helper, route both tools and reflect through them, and the bug list collapses to two or three fixes rather than a rewrite.

## node-editing — Grade D (needs-rework)

This subsystem has a fundamental architectural fracture: the node editor (directSelectTool) ships its OWN regex-based path parser/serializer that is incompatible with the robust parsePathD/commandsToD parser used by every other tool (selectTool, freeTransform, knife, join, PDF export, reflect, grafting). The directSelect parser silently mishandles relative commands (m/l/c treated as absolute), ignores H/V/S/Q/T/A entirely, and drops them on the floor when rebuilding the d string — so direct-selecting any path that came from an imported SVG, a non-path auto-conversion, or its own auto-convert-to-path flow will corrupt or destroy geometry. On top of that there are concrete data-loss interlocks: the auto-convert-to-path flow holds a stale element ref across undo, and several edge-case math/serialization bugs in pathOps. The pen tool is the most solid piece. The DI-by-getter design and the pure functions are testable (and tested), but the existing tests only ever feed absolute, space-separated, M/L/C input — they validate the happy path the parser was written against, which is exactly why the corruption bugs survived. This is fixable but the node editor must be rebuilt on top of parsePathD; do not salvage the bespoke parser.

_Architecture:_ The design is reasonable on paper: tools are factories taking getter injections (getSvg/getDoc/getHistory), edits go through a command/history layer, and the core geometry (pathOps, pathSimplify, pen buildPathD) is pure and unit-tested. The fatal flaw is duplication of the single most important primitive: there are TWO path parsers with different capabilities and different coordinate assumptions, and the powerful one (parsePathD, which normalizes relative/H/V/S/Q/T/A to absolute M/L/C/Z) is NOT the one the node editor uses. That is the root cause of the worst findings and the source of cross-tool interlock corruption (convert-to-path then node-edit destroys geometry). It is under-engineered where it matters (node editor parser) and not over-engineered elsewhere. Testability is good structurally but the existing tests are a false comfort — they only feed absolute, well-spaced M/L/C input, which is precisely the subset the buggy parser handles, so they pass while real imported/converted paths break. Recommendation: keep penTool and pathOps, rebuild the directSelect node editor entirely on top of parsePathD/commandsToD, add tests with relative + H/V/S/Q/T/A + compound-path fixtures, and add node-level Delete/Escape handling.

## draw-tools — Grade C (fixable)

The shape tools (rect, ellipse, line, pencil, eyedropper) are genuinely solid: a clean, consistent factory pattern with getSvg/getDoc/getHistory closures, preview elements tagged data-role="preview" (correctly stripped on export/save), grid+point snapping, locked-layer guards, and a uniform "create -> select -> switch to select tool" finish. They do not warrant a rewrite. The rot is concentrated in the text subsystem and a couple of cross-module interlocks. The worst issue is a keyboard interlock: while the text tool holds keyboard capture, EditorContext deliberately lets ALL Ctrl combos through (line 63: `if (isKeyboardCaptured() && !e.ctrlKey) return`), so Ctrl+Z/C/V/X/D/G/A fire global document operations mid-text-edit instead of being suppressed — exactly the historical "inputs swallowing shortcuts" fault, inverted. The text tool also commits a hardcoded 16-unit font into an mm document space (A4 = 210x297mm), producing a ~16mm-tall glyph (~45pt) for every text object. The eraser's multi-element undo can throw NotFoundError when erased siblings are restored out of order. areaText.ts is dead, unwired code with incoherent mm/px units. Hand-rolled text caret/selection/measurement is the under-tested, high-maintenance liability; a staff engineer would not approve the text path as-is, but everything else is shippable after targeted fixes.

_Architecture:_ The factory-per-tool pattern (closures over getSvg/getDoc/getHistory, a ToolConfig with handlers + onDeactivate, registry-driven dispatch) is sound, consistent, and genuinely testable for the shape tools — pointInPolygon, measureDistance, snapLineAngle, computeRect/computeEllipse are pure and unit-test-friendly. Preview lifecycle (data-role='preview' + central OVERLAY_SELECTOR stripping in fileio) is a clean separation of editor chrome from document. The two real architecture smells are: (1) keyboard ownership is split across Canvas.tsx and EditorContext.tsx with capture gating that leaks Ctrl combos (finding 1) — keyboard routing should be a single dispatcher that respects capture wholesale; (2) the text tool reimplements a text editor (caret blink, selection ranges, substring measurement) by hand against raw SVG, which is the under-tested, high-bug-density part and the main argument for reworking specifically the text path (e.g. a contentEditable/foreignObject or a dedicated text-edit model). Units are a latent hazard: the codebase is mm-native but font sizes and areaText assume px without conversion. Verdict: keep and harden the shape tools; rework the text subsystem and delete areaText.ts. This is a fix-this-part situation, not a full rewrite.

## tool-infra — Grade B (fixable)

The in-scope modules are individually small, clean, and well-tested — registry.ts, defaultStyle.ts, markers.ts and guides.ts are each tidy singletons with a swap-the-active-instance pattern that supports multi-document. This is NOT rewrite territory. The real defects live at the INTERLOCK boundary, not inside these files: keyboard input is dispatched by THREE independent uncoordinated window keydown listeners (useToolShortcuts, Canvas, EditorContext), and the only coordination mechanism is the single boolean `keyboardCaptured`. That boolean is too coarse: during text editing it correctly suppresses single-key tool shortcuts but deliberately lets Ctrl-combos through to EditorContext, so Ctrl+Z/X/V/C while typing operate on the document/selection instead of the text — a genuine chained-failure bug. Separately, two of the in-scope files (the `ToolConfig.icon` field and the entire iconKeyForTool module) are dead in production: LeftRail hardcodes its own icon keys AND its own shortcut letters, so the registry's icon/shortcut data and the visible UI can silently drift. guides.ts has an asymmetric reset() that wipes subscribers without notifying. Nothing here loses or corrupts a saved document, hence B not C/D — but the keyboard interlock is a real user-facing footgun and the dead-code/drift is exactly the kind of rot that makes an owner want to rewrite.

_Architecture:_ The core design is sound and intentional: each concern (registry, default style, guides, markers) is a tiny module-singleton with a getActive/setActive-instance swap so multiple documents can each own their own state bundle, wired centrally in documentState.setActiveDocument. That pattern is clean, testable (every file has a focused test), and not over-engineered. The weakness is not inside these files — it is the absence of a single keyboard-input owner. Input handling is smeared across three window listeners coordinated only by one coarse boolean (keyboardCaptured), which is structurally why the text-edit Ctrl-combo bug exists and why guard logic is duplicated and already inconsistent. Secondary rot: the registry carries icon and shortcut data that the actual UI (LeftRail) duplicates by hand, so the registry is the source of truth in name only and two whole units (ToolConfig.icon, iconKeyForTool) are dead. Recommendation: keep the modules, centralize keyboard dispatch, and either make LeftRail consume the registry or delete the unused fields — a few days of focused work, not a rewrite.

## properties-ui — Grade C (fixable)

This subsystem is competently structured but has a cluster of real interlock/undo defects concentrated in gradient handling and transform editing. The dominant problem is that gradient creation mutates the document <defs> OUTSIDE the command/history system, so undo/redo and document state desync, and every fill-type toggle leaks an orphan gradient. Transform editing in the ControlBar can silently destroy a baked matrix (scale/translate) when rotation is set to 0. The color/default-style plumbing and the controlled-input pattern are sound and well-tested-looking. Nothing here is unsalvageable; the bugs are localized and fixable without a rewrite, but they are exactly the "feature A leaves state that breaks feature B (undo)" class the owner is worried about.

_Architecture:_ The design is reasonable and mostly testable: a single source of truth (the live SVG DOM), a thin command/history layer (ModifyAttributeCommand/CompoundCommand) with a clean undo/redo stack, pub/sub for selection + default-style + history-tick re-derivation, and a consistent controlled-input pattern (local editing state synced on blur, Escape-to-revert) reused in both panels. Testid hooks and the milestone comments show genuine test discipline. The core flaw is a leaky abstraction boundary: not all document mutations go through the history layer — gradient <defs> creation (and to a lesser degree direct setAttribute in a few handlers) sidesteps it, which is precisely what produces the undo desync and the defs leak. PropertiesPanel.tsx is also overgrown (~725 lines, deeply nested IIFEs returning JSX) and duplicates frame/transform logic that already exists in ControlBar; consolidating the per-tag geometry math into one shared module would shrink both and remove the path/g read-only-input divergence. Verdict: salvageable — enforce 'every document mutation is a Command', add a defs GC / gradient-reuse pass, fix the matrix-clear, and de-duplicate the geometry, and this subsystem reaches B/A without a rewrite.

## app-shell — Grade C (fixable)

The shell architecture is fundamentally reasonable: a thin React layer over imperative DOM/SVG singletons, with a command-history undo stack and a per-document state bundle that anticipates multi-doc. Coordinate math (screenToDoc via getScreenCTM) is correct and reflect bakes transforms into geometry to avoid leftover scale() matrices — both are signs of a developer who learned from past fault-lines. However the subsystem carries several real, user-visible interlock bugs: Document Setup is silently broken (dialog updates React state but never the artboard model that Canvas actually reads), the ruler drag-to-guide feature emits guides on the wrong coordinate axis (X used as a horizontal guide's Y, and vice versa), keyboard shortcuts fire while a Properties-panel <select> is focused because the input guard only covers INPUT/TEXTAREA, and Shift+Ctrl+' toggles grid visibility instead of snap due to branch-ordering. None are unfixable; the bones are sound enough that a rewrite is not warranted, but the owner's frustration is justified — these are exactly the chained-state failures they flagged, and they ship today. Testability is mediocre: the heavy reliance on module-level singletons and direct window listeners makes the routing logic hard to unit-test, which is why these bugs survived.

_Architecture:_ The design is a deliberate hybrid: React owns chrome/layout and the imperative SVG/DOM owns the document, with module-level singletons (selection, guides, artboard, grid, tool registry) plus a command-history undo stack. This is a sensible choice for a vector editor and the seams (DocumentState bundle, setActiveDocument) show genuine forethought toward multi-document. It is neither over- nor under-engineered for its size. The real weakness is testability and discipline around the singletons: event routing is spread across three independent window listeners (EditorContext, Canvas, useToolShortcuts) with implicit ordering and three slightly different input-focus guards, which is precisely why the <select> leak and the Document-Setup desync survived. The two most damaging bugs (app-shell-1, app-shell-2) are pure state-propagation/coordinate mistakes, not architectural rot — they are localized and cheap to fix. Recommend consolidating keyboard routing into a single dispatcher with one shared 'is editable target' predicate, and driving the Canvas viewBox from the artboard model rather than a parallel React `dimensions` prop, before considering anything more drastic.

## graft-engine — Grade B (solid)

This is a genuinely well-engineered subsystem, not a rewrite candidate. The modules are small, pure, single-responsibility, and heavily unit-tested (12 test files). The hard parts — redaction-before-font-registration ordering, the Y-flip round-trip through redaction, Identity-H TJ shaping with GPOS adjustments, font subsetting — are correct and the inline reasoning is unusually disciplined. The owner's frustration is more likely with FIDELITY GAPS than with broken architecture. The real defects cluster in two places: (1) the integration seam in fileio.ts/ensureFontIfNeeded only ever feeds Carlito-Regular, so all NEW bold/italic overlay text silently renders upright-regular even though the multi-slot registry that would fix it already exists and is tested; (2) the two transform-composition paths (walkLayer vs emitElementWithAncestors) disagree about whether a layer's OWN transform is applied, and graftCs drops group-inherited fill/stroke/opacity entirely. None of these corrupt the PDF or lose data; they produce visually-wrong output in specific cases. Grade B: ship-quality bones, with a handful of real correctness gaps to close.

_Architecture:_ The design is sound and notably disciplined: each module is pure and single-purpose (graftCs = op emission, graftBbox = AABBs, graftClassify = layer triage, graftMupdf = native lifecycle, graftShape = shaping, graftExport = orchestration), and the seams are clean enough that the heavy logic is unit-testable without spinning up a real PDF — borne out by the 12 graft*.test.ts files. The redaction-before-font-registration ordering and the redaction Y-flip round-trip are both correct and, more importantly, the WHY is documented inline, which is exactly what you want in a coordinate-space minefield. It is neither over- nor under-engineered for an MVP. The genuine weaknesses are at the integration boundary, not the core: fileio.ts hands the engine only Carlito-Regular (wasting the bold/italic infra that already exists and is tested), the two transform-composition paths disagree about layer-level transforms, SVG style inheritance (group fill/opacity) is unmodeled, and several coordinate assumptions (MediaBox origin = 0,0; text rotation) are unstated. Salvageability is high — these are targeted fixes, not a rewrite. Recommend NOT rewriting; instead close graft-engine-1/2/3 first, then the coordinate-assumption items.

## pdf-io — Grade C (fixable)

The core architecture is sound and more disciplined than the owner fears: the worker boundary is clean, the SourcePdfStore/graft-vs-pdf-lib routing has a clear contract, coordinate conversions are mostly consistent (no double Y-flip in this path — drawText flips via svgPtToPdf, drawPath relies on drawSvgPath's internal flip, and the two never compound), and the export engine is deterministic and testable. What drags the grade down is a genuine state-leak interlock class: the SourcePdfStore is never cleared on the paths that logically invalidate it (Open SVG, layer delete, New Document), so stale ~10MB byte buffers and stale source-id mappings survive document changes. That's exactly the chained-failure category the owner flagged, and it's the most important thing to fix. The pdf-lib fallback engine also silently drops rotation, bold-serif, and most colors — wrong output rather than a crash. Debug console.log/console.warn spam is shipped in the hot path. None of this requires a rewrite; it's a focused cleanup pass.

_Architecture:_ The design is fundamentally sound and notably better than the 'consider a rewrite' framing suggests. The worker boundary (pdfRender.ts pure / pdfRender.worker.ts shim / pdfImport.ts pending-map) is clean, cancel-safe, and rejects all pending requests on worker death. Coordinate handling is the usual mm↔pt↔PDF-pt minefield but is actually consistent here: there is NO double Y-flip in this subsystem — drawText flips via svgPtToPdf while drawPath deliberately does not and leans on drawSvgPath's internal flip, and the comments document why. Leaf-vs-container transform handling is correctly applied to leaves in walk(). The real weakness is lifecycle/teardown discipline: SourcePdfStore has a clear contract on paper but its teardown half is dead code, so document-replacing and layer-deleting operations leave stale source state — the exact interlock class to fear, and the reason for the C. The pdf-lib fallback engine is honestly under-built (rotation/color/weight gaps) but it is self-aware about being MVP and is well isolated and testable (pure svgStringToPdfBytes, deterministic metadata pinning for golden byte-match). Testability overall is good (most functions exported for tests, pure pipelines). Recommendation: salvage, do not rewrite — fix the store teardown wiring first (pdf-io-1/2/10), then harden the pdf-lib primitive path (pdf-io-3/4/5).

## fonts — Grade B (fixable)

This is competent, well-documented, mostly-pure model code. The three files are individually clean: tagging is trivially correct, font extraction handles the Type0-descendant and standard-14-null edge cases deliberately (with comments that match mupdf reality), and the snapshot/diff logic is sound for the attribute-only scope it claims. I found NO crash/corruption bug in the read paths. The real problems are INTERLOCK and dead-code issues: (1) an entire count-based deletion-detection API (expectedSourceCount/currentSourceCount/SOURCE_COUNT_ATTR) is dead — nothing in production calls it, yet snapshotImportedElements still stamps data-vf-source-count onto every imported layer, which then serializes into saved/exported SVG as junk metadata; (2) the documented 'text content tracked at Command level' contract is vaporware — commandTouchesSource is consumed nowhere outside commands.ts, and there is no text-content-edit command, so the moment Phase-3 in-place text editing lands, edited source text will silently classify as graft and be lost; (3) findRemovedElementBboxes uses layer.contains(el), so moving a source element to another layer is misreported as a deletion and gets masked over; (4) the snapshot WeakMap and registry are in-memory only and never rebuilt on SVG reload, so the whole edit-detection state is session-scoped (currently masked by the SourcePdfStore also being session-scoped, but a latent footgun). This is salvageable — none of it is rewrite-grade structural failure, it's accumulated half-wired features and stale doc-comments.

_Architecture:_ The decomposition is sound and genuinely testable: three single-responsibility pure modules (tagging = DOM attr stamps, font = mupdf-object reads, snapshot = WeakMap diff), each with a focused test file, no DOM mutation outside tagImportedLayer/snapshotImportedElements, no I/O. Edge-case handling in sourceFont.ts (Type0 descendant descent, standard-14 PDFObject.Null guards, WASM-slab copy-out) is unusually careful and the comments are accurate to mupdf behavior — this is the strongest file. The weakness is at the SEAMS, not inside the modules: the subsystem has two parallel, partly-dead deletion-detection mechanisms (count attr vs bbox registry), a documented-but-unwired text-content/Command contract, and several latent hardcodes (page 0, pageKey-vs-fontKey identity) that are correct only by accident of 'imports are always single-page page 0'. It is mildly over-engineered (WeakRef+UID registry, count attr) for what is currently exercised, and under-engineered on persistence (all edit-detection state is session-scoped and silently relies on the source store also being session-scoped). Verdict: keep all three modules, but prune the dead count API, fix the contains()-based removal and page-0 hardcodes, and either implement or delete the text-content/Command path before Phase-3 in-place editing lands.

## geometry-core — Grade B (solid)

This subsystem is the healthiest part of the app I have seen. The matrix math is correct (multiply/invert/apply/parseTransform all compose in the right SVG left-to-right order), the pub-sub state singletons (grid/wireframe/activeLayer/artboard/smartGuides) are clean and consistent, and the transform-aware AABB pipeline is genuinely the single source of truth it claims to be. There is no double-Y-flip, no leaf-vs-container confusion in the move path (computeTranslateAttrs and selectTool.moveElement both correctly compose T*M for groups and shift rotate-centers for attr-positioned shapes), and the smart-guide candidate cache lifecycle is correctly opened/closed around drags. The real defects are concentrated and mostly edge-case: decomposeMatrix mis-reports scaleY/skewX under shear; two rotate-center regexes disagree on scientific-notation support; smart-guide line emission has tie/dup quirks; and a handful of NaN-silently-propagating parse paths. None are data-loss or corrupt-export class. This does not need a rewrite — it needs a half-day of targeted fixes plus a few decompose/skew unit tests.

_Architecture:_ The design is sound and notably disciplined for a 25K-LOC editor: one affine Matrix type with pure functions, one transformedAABB used uniformly by hit-test, smart guides, align, and the control bar, and a consistent module pattern (private class + module-level `active` singleton + thin free-function facade + reset()) across grid/wireframe/activeLayer/artboard/smartGuides that makes per-document teardown trivial. It is testable — matrix.ts is pure and already has decent unit coverage (the decompose-with-shear gap is a test omission, not an architecture flaw); the geometry/DOM-touching functions are harder to unit test but are thin wrappers. Mild under-engineering risks: regex-based transform mutation is duplicated in at least five files with subtly different patterns (the geometry-rotate-regex finding) and should be centralized into matrix.ts helpers; coordinate units (mm vs px) are correct but enforced only by convention/comments, not types, so a typed Mm/Px brand would prevent a whole class of future mix-ups. Overall this subsystem does NOT justify a rewrite — it is the load-bearing, correct core; spend the effort hardening parse paths and consolidating the duplicated rotate-center regex instead.

## commands-state — Grade C (fixable)

The command/undo core (CommandHistory, the leaf command classes) is clean, small, and correctly structured — execute/undo are symmetric for the simple cases and the touchesSource() plumbing for the graft exporter is thoughtful. The rot is concentrated at the interlock seams, exactly where the owner feared: (1) paste leaks duplicate IDs into the document because only the top-level pasted element is re-ID'd while all transferred descendants keep their original ids, corrupting every subsequent id-based lookup; (2) GroupCommand mishandles cross-layer and out-of-DOM-order selections, so undoing a group moves elements to the wrong layer / wrong z-position; (3) no command in the subsystem restores selection on undo/redo, and the live selection array is never purged when elements are removed, leaving stale Element refs in selection state after cut/delete. None of these are crashes, but several are silent data/structure corruption that only surfaces later — classic chained-failure bugs. This is fixable without a rewrite; the architecture is sound, the bugs are localized.

_Architecture:_ The design is fundamentally sound and refreshingly small: a flat Command interface with symmetric execute/undo, a 200-entry CommandHistory with a clean subscribe/notify, and well-factored operation modules (clipboard/nudge/zOrder) that were deliberately extracted from EditorContext for testability — that intent is good and pays off. It is neither over- nor under-engineered for a single-document editor. The two structural weaknesses: (1) selection is treated as orthogonal to the command system, so no operation snapshots/restores selection and the selection array holds raw, never-purged Element references — selection lifecycle should be owned by CommandHistory (snapshot ids around execute/undo/redo) rather than scattered clearSelection() calls in callers. (2) DocumentState's pointer-swap multi-document scheme is elegant on paper but the subscriber model captures instances at subscribe time, so the advertised Phase-2 will break without a re-bind step. Testability is decent for the leaf commands (they take plain Elements + a DocumentModel) but the interlock bugs found here are precisely the ones unit tests miss — they need DOM-round-trip and cross-layer fixtures. Salvageable: fix the id-uniquification on paste, make Group capture per-child parent/sibling, and centralize selection in the history; no rewrite warranted.

## panels-chrome — Grade C (fixable)

This is presentational chrome that is mostly competent React, but it has a cluster of real interlock and correctness defects concentrated in LayersPanel, plus a fully dead theme subsystem. The two most damaging bugs: (1) layer visibility/lock toggles bypass the command history entirely, so hiding a layer is not undoable, never marks the doc dirty (status bar still says "Saved"), yet DOES affect export/serialize — a silent data-divergence trap; and (2) addLayer mutates DOM z-order OUTSIDE the AddElementCommand, so redo replays the element to the wrong stacking position. Layer rows are also displayed in raw DOM order (bottom-painted layer at the top of the list), inverting the universal design-tool convention, which makes the move-up/move-down arrows move layers the "wrong" way relative to z-order. The theme/atrium.ts file (4 palettes, ~70 LOC) has zero importers and CSS variables are hand-duplicated in index.css, so the file is dead weight that will silently drift. IconGlyph hardcodes a dark ink stroke color instead of currentColor, so active-tool color theming and any non-light palette are broken at the icon level. Nothing here justifies a full rewrite — the bugs are localized and the styling is consistent — but LayersPanel's state/command discipline needs a real pass.

_Architecture:_ The design altitude is right: small, mostly pure presentational components, a clean IconGlyph dictionary, and a sensible Panel primitive. The rot is in state discipline, not structure. LayersPanel is the weak link: it tracks the active layer by positional index into a stale-closure array AND drives a global module-singleton (activeLayer) that every drawing/clipboard tool reads via getActiveLayer() — so the panel is a high-traffic interlock surface, yet it mutates DOM (visibility, lock, z-order) outside the command system, splitting the source of truth between the history stack and the live DOM. That split is the root cause of findings 1-3 and is the single most important thing to fix. Theming is half-built and dishonest: atrium.ts is dead, CSS vars are hand-copied, and several components hardcode rgba/oklch literals (findings 4,5,8), so the advertised theme switcher would visibly break today. Testability is mediocre — there are good data-role/data-testid hooks, but index-based keys and the index-based active-layer model make reorder/delete behavior hard to assert deterministically. Verdict: salvageable. Fix the command-vs-DOM split in LayersPanel, switch active-layer tracking to element identity, make icons use currentColor, and either wire or delete atrium.ts; no rewrite warranted.
